### R61-V1 — 한글만 고치면 옛 영어가 그림의 실제 행동이 됩니다

우선순위: **P1** · 감사 A의 잔여 문제.

재현:

1. 원래 글은 “유하가 숲에서 큰 나무를 올라가요.” / “Yuha climbs a tall tree in the forest.”
2. 앱의 `applyPageText`로 한글만 **“엄마가 집에서 물을 마셔요.”**로 수정합니다. 영어는 아직 맞추기 전입니다.
3. `sceneGenerationRequest`를 호출합니다.
4. 새 지문 비교가 글 변경을 알아차리지만, `Actual event`는 여전히 **“Yuha climbs a tall tree in the forest.”**입니다.
5. 참조 시트도 유하만 들어가고, 장소는 숲으로 남습니다.

원인:

- `dist/image-generation/scene-prompt.js:217`: 오래된 장면 처리에서 `currentNarrative.en || currentNarrative.ko`를 선택합니다. 영어가 존재하면 한글 변경보다 옛 영어를 우선합니다.
- 지문은 전체 한글+영어가 달라졌다는 것만 알려 줍니다. 어느 언어를 언제 고쳤는지, 번역이 현재 원문과 맞는지는 구별하지 않습니다.
- `scene.who`와 장소/참조 선택은 옛 계획에 계속 의존합니다.

R61 테스트는 ‘새 글로 그리라’는 문구가 생겼는지만 확인합니다. **현재 사건·인물·장소가 실제로 요청에 들어갔는지**까지 확인해야 합니다.

보완안:

- 그림의 기준 원문과 그 원문을 바탕으로 만든 영어의 지문을 구별합니다.
- 기준 원문이 바뀌면 옛 영어를 `Actual event`로 쓰지 않습니다.
- 사건뿐 아니라 등장인물·장소·소품·참조 목록도 같은 새 장면 기준으로 갱신합니다. 한 문장만 바꾸어 해결됐다고 처리하지 않습니다.
- 추가 유료 그림을 사기 전에 계획 갱신 또는 해당 쪽 확인을 끝냅니다. 이미 산 그림은 보존합니다.

증거: `QA/r61-verification/recheck.json`의 `edited`, `edited-page-request.txt`.

### R61-V2 — 쪽 수가 바뀌면 수정 범위 보호가 사라집니다

우선순위: **P1** · 감사 D의 잔여 문제.

실제 `runRoomDrafts` 경로에서 독자단은 2쪽만 고치라고 했습니다. 계산된 허용 범위도 1·2·3쪽입니다. 그런데 가짜 모델이 8쪽을 “외계인이 유하를 화성으로 데려가요”로 바꾸고 끝에 한 쪽을 추가하면:

```json
{"pages":[1,2,3],"restored":[],"structural":true}
```

가 반환되며 **8쪽의 새 사건이 그대로 수용됩니다.** 독자단이 웃었다고 지정한 8쪽도 보호되지 않습니다.

원인: `dist/story-generation/writers-room.js:1530`의 `mergeRewrite`가 쪽 수가 다르면 수정본 전체를 그대로 반환합니다. 이는 새 weave 6 실제 경로에서 호출됩니다.

추가로 같은 쪽 수에서도:

- 한글이 같으면 그림 메모를 바꾸어도 그대로 수용합니다 (`:1537`).
- 범위 밖 모든 쪽에 문장 하나를 추가하는 것은 ‘복선’인지 확인하지 않고 수용합니다.

보완안:

- 국소 수정에서는 안정적인 쪽/항목 ID로 변경을 적용합니다.
- 구조 변경을 요청하지 않았는데 개수가 달라진 응답은 원문을 보존하고 별도 제안으로 남깁니다. 전체를 자동 교체하지 않습니다.
- 보호 대상은 한글만이 아니라 그림 메모·펼침 표시도 포함합니다.
- 복선 추가는 무제한 예외가 아니라, 명시한 대상과 근거가 있는 변경으로 다룹니다.

증거: `recheck.json`의 `rewritePipeline`은 실제 초고 단계 실행 결과, `rewrite`는 각 허점의 작은 직접 재현입니다.

### R61-V3 — 영어 누락이 최종 쪽에서 다시 한글로 채워집니다

우선순위: **P1** · 감사 H의 잔여 문제.

재현:

1. weave 6 영어 응답에서 3쪽만 누락합니다.
2. 보충 요청 1회에도 3쪽이 오지 않게 합니다.
3. 초고 단계는 `englishMissing:[3]`, 해당 영어는 없음으로 정상 기록합니다.
4. 그 결과를 실제 `runRoomPages`와 `toLegacyPages`에 넘깁니다.
5. 최종 3쪽의 영어가 한글 **“콩이는 어디 있게?”**로 채워집니다.

원인: `dist/story-generation/writers-room.js:2235`의 `textEn: p.en || p.ko`가 새 경로에서도 남아 있습니다. 새 `full-auto.js:1625` 안내도 “한글이 영어 자리에 들어가 있으니”라고 설명합니다.

즉, ‘조용히 대체하지 않는다’는 부분은 안내로 개선됐지만 **한글을 영어로 대체하지 않는다**는 데이터 문제는 남았습니다. R61 테스트는 `runRoomDrafts`의 `en === undefined`에서 끝나 다음 단계의 대입을 놓칩니다.

보완안:

- 새 경로의 누락 영어는 `""`와 명시적인 누락 상태로 보존합니다.
- 검사·검수·읽기·인쇄가 누락을 구별하도록 연결합니다. 한글 원고는 계속 보존하고, 영어 칸에 중복 출력하지 않습니다.
- ‘영어를 한글에 맞추기’로 보완한 뒤 누락 표시를 해제합니다.
- 정상 영어 및 이미 받은 응답을 보존하고 전체를 재구매하지 않습니다.

증거: `recheck.json`의 `english`: 영어 요청은 2회(최초+보충), 초고의 영어는 null, 최종 영어는 한글과 동일.

### R61-V4 — 시트 없는 인물의 생김새가 책에 고정되지 않습니다

우선순위: **P1** · 감사 B의 후속 문제.

실제 FULL AUTO로 만든 한 쪽짜리 사슴은 처음 요청에서 “금빛 귀 하나”가 전달됩니다. 여기까지는 수정됐습니다. 이후 서랍 카드를 “보라색 용, 빨간 뿔 셋”으로 바꾸면 **이미 만든 같은 책의 그림 요청도 용으로 바뀝니다.** 카드를 삭제하면 고유 생김새가 사라집니다.

원인: `dist/image-generation/world.js:881`에서 시트 없는 인물은 `state.characters`의 현재 카드를 읽습니다. 책의 `storyInput.characters`에는 금빛 귀를 가진 사슴 정보가 이미 동결되어 있는데 그것을 쓰지 않습니다.

시트가 있는 인물은 동결한 스냅샷을 쓰고, 시트가 없는 인물만 서랍 편집의 영향을 받습니다.

보완안:

- 시트가 없더라도 책에 동결된 인물 정보를 우선 사용합니다.
- 서랍 편집·삭제는 이후 새 책에 적용하고, 현재 책에는 명시적인 갱신 동작이 있을 때만 반영합니다.
- 다음 편에서도 해당 인물을 이어 쓸 수 있도록 ‘시트 구매 제외’와 ‘책의 인물 목록 제외’를 구별합니다.

증거: `recheck.json`의 `identity`: `frozenInputHasGoldEar:true`, 수정 후 `afterHasDragon:true`, 삭제 후 `afterDeleteHasIdentity:false`.

## 3. 기존 책 호환성 설명도 정정이 필요합니다

‘weave 5 이하와 기존 책의 요청이 바이트 단위로 동일’이라는 설명은 현재 구현 전체에는 맞지 않습니다.

동일한 weave 5 / `pictureRefs.version:2` 입력을 운영 R60 함수와 R61 함수에 넣어 비교했습니다.

- 빈 등장 목록: R60은 유하·엄마 시트 4개, R61은 0개를 보냅니다.
- 글자가 지정된 장면의 최종 그림 요청도 달라집니다.
- 시트 없는 인물을 보존하는 B의 FULL AUTO 수정은 `hasRoomKept`라서 weave 6에서만 켜집니다. weave 5 테스트는 의도적으로 인물 삭제를 유지합니다.

수정된 참조 동작 자체가 더 나을 수는 있지만, 적용 대상과 호환성 주장은 정확해야 합니다. 기존 요청을 보존할지, 특정 결함만 이전 작업에도 고칠지 정책과 테스트를 일치시켜야 합니다. 이미 산 결과를 삭제하거나 소급 재구매할 필요는 없습니다.

증거: `recheck.json`의 `compatibility`.

## 4. 재현 방법

제품 코드는 수정하지 않습니다. Node 24, 가짜 엔진, `fetch` 차단으로 실행합니다. 기존에 구매한 원고의 글만 `QA/r60-text/manuscript.json`에서 읽습니다. API 키나 실제 그림이 필요 없습니다.

```bash
DONGHWA_APP_ROOT=/absolute/path/271/donghwa-workshop \
DONGHWA_AUDIT_OUT=/absolute/path/r61-output \
node QA/r61-verification/tools/recheck.mjs
```

이전 운영 코드와 비교하려면 선택적으로 `DONGHWA_R60_ROOT`를 R60 앱 루트로 지정합니다. 지정하지 않아도 weave 6의 다섯 사례는 실행됩니다.

출력 `recheck.json`의 `acceptance` 다섯 값은 모두 false였습니다. 이는 기존 1,203개 테스트의 실패를 뜻하지 않습니다. 이번에 확장한 승인 조건을 아직 만족하지 못한다는 뜻입니다. 스크립트 종료 0만 보지 말고 이 값과 `blockingFindings`를 확인해야 합니다.

`edited-page-request.txt`에는 실제로 조립한 잘못된 요청이 들어 있습니다. 시트 주소는 `https://qa.invalid/`의 가짜 주소입니다. 원본 책장 백업·API 키·PIN·그림은 저장소에 넣지 않습니다.
