# Codex Sites 배포 안내

## 배포 구조

이 앱은 Codex의 Sites 플러그인을 통해 배포합니다. 운영 서버는 Cloudflare Workers,
업무 DB는 D1(`DB` 바인딩), 사진은 비공개 R2(`BUCKET` 바인딩)를 사용합니다.
`DATA_DIR`, Railway Volume, Docker 컨테이너는 Sites에서 사용하지 않습니다.
외부 npm 패키지 없이 기존 화면과 API를 유지했습니다.

- 운영 주소: https://erp.seoulsemi.com (회사 도메인, AWS Route 53 서브도메인 연결·HTTPS 인증 완료)
- 기존 Sites 주소: https://eachdoll-work-process-hub.seoulsemitec-3654.chatgpt.site (계속 유지)
- 배포 대상은 저장소의 `work-process-app/` 내용만입니다. 저장소 루트의 다른 프로젝트는 배포하지 않습니다.
- `.openai/hosting.json`의 `project_id`가 기존 Site를 식별합니다. 후속 작업에서 새 Site를 만들거나 이 값을 바꾸지 마세요.
- Sites 소스 저장소는 GitHub 원본 저장소와 별개입니다. GitHub에 커밋하는 것만으로 Sites가 자동 재배포되지는 않습니다.

## 처음 사용하기

1. 위 주소를 엽니다. Sites의 공유 설정에 따라 ChatGPT 접근 인증이 적용될 수 있습니다. 현재 공유 범위는 Sites 설정에서 확인하세요.
2. 앱의 **가입** 화면에서 이름, 비밀번호, 설정한 초대코드를 입력합니다.
3. 앱에 처음 가입한 계정이 관리자입니다. 기존 가입자는 같은 이름과 비밀번호로 로그인하세요.
4. **관리자 설정**에서 초대코드를 변경하고 담당자의 구매·품질·개발·생산·물류 권한을 지정합니다.
5. 직원에게 접근을 허용하려면 Sites의 공유 설정에서 대상 사용자를 추가해야 합니다.
   ChatGPT Site 접근 권한과 앱 내부 가입·업무 권한은 별도로 적용됩니다.
   배포 과정에서는 현재 공유 범위를 그대로 유지합니다.

## 백업

1. 관리자 계정으로 로그인하고 **관리자 설정 → 전체 백업 다운로드**를 누릅니다.
2. 백업 중에는 다른 사용자의 입력·수정·사진 삭제를 잠시 멈춥니다. 표별로 나누어 읽으므로
   사용 중의 전체 데이터에 대한 단일 시점 스냅샷은 아닙니다.
3. 다운로드 폴더에서 `work-process-backup-YYYY-MM-DD.json` 파일을 확인합니다.
4. 파일에는 업무 기록, 계정의 비밀번호 검증값, 초대코드, 사진 원본이 포함됩니다.
   로그인 세션은 제외합니다. 접근이 제한된 회사 백업 저장소에 보관하세요.
5. 재배포는 기존 D1/R2를 유지하므로 데이터를 초기화하지 않습니다. Site 자체를 삭제하지 마세요.

백업은 서버에서 200행씩 읽고 사진을 차례로 받아 브라우저에서 파일로 만듭니다.
사진이 많으면 브라우저 메모리와 다운로드 시간이 늘어납니다. 실패 메시지가 나오면 해당 파일을
완전한 백업으로 취급하지 말고 다시 받으세요. 자동 백업 일정은 아직 설정하지 않았습니다.

복원은 자동 덮어쓰기 버튼을 제공하지 않습니다. 복원 전에 현재 DB/사진을 별도로 백업하고,
백업 형식·계정·사진 참조를 검증한 뒤 관리 권한이 있는 작업으로 진행해야 합니다.
소스 버전 되돌리기는 데이터 복원과 다릅니다.

## 기존 Node.js 버전 데이터

이번 배포는 새 D1/R2로 시작합니다. 기존 `data/app.db`나 사진을 제공받지 않았으므로 자동 이관하지 않았습니다.
기존 데이터가 있다면 먼저 앱을 중지하고 `data/` 전체를 별도로 백업하세요.
기존 버전은 scrypt, Sites 버전은 Web Crypto PBKDF2-SHA256(100,000회)을 사용합니다.
기존 계정의 해시를 그대로 복사하면 로그인할 수 없으므로 별도 데이터 이관과 비밀번호 재설정 계획이 필요합니다.

## 로컬 실행과 확인

Node.js 22.13 이상에서:

```bash
cd work-process-app
INVITE_CODE=local-test-code npm start
npm test
npm run build
```

로컬은 `local.mjs`가 SQLite와 파일 저장을 통해 동일한 Worker API를 실행합니다.
운영 D1/R2와 로컬 `data/`는 별개입니다.
`GET /api/me`는 비로그인 상태에서 HTTP 200과 `{"user":null}`을 반환합니다.
HTTPS 로그인 쿠키는 HttpOnly + Secure + SameSite=None + Partitioned를 사용하여 Sites가 포함된 화면에서도 세션을 유지합니다. 로컬 HTTP에서는 SameSite=Lax를 사용합니다.
비공개 Sites 운영 주소에서는 그 앞단의 ChatGPT 접근 인증이 먼저 적용됩니다.

Dockerfile과 railway.json은 기존 Node 로컬 실행 경로를 위한 참고 파일로 남아 있으며 Sites 배포에는 사용하지 않습니다.

## 입고 자동 수입검사

`0002_receipt_analysis_links.sql`은 분석 기록에 입고 출처와 원본 ID, 중복 방지 인덱스만 추가합니다.
기존 기록은 유지하며 데이터 삽입이나 일괄 이관을 마이그레이션 SQL에 포함하지 않습니다.

발주입고의 **입고확인**과 기타입고의 **등록**은 분석리스트에 `수입검사 / 대기`를 함께 생성합니다.
각 입고와 분석 등록은 D1 트랜잭션으로 처리합니다. COA 요청 여부와 관계없이 분석 건을 생성하며,
COA 요청 발주는 분석 양식의 결과 유형에도 COA발행을 표시합니다.
반복 입고확인에서는 기존 분석 상태·결과를 유지합니다. 이후 원본 수정/삭제는 분석 이력을 변경하지 않습니다.

## BOM 및 사진 첨부 배포

`0003_bom_and_attachments.sql`은 BOM/첨부 테이블과 생산일정의 BOM 참조·스냅샷 컬럼을 추가합니다.
기존 계정·일정·의뢰·물류 데이터는 유지합니다. 추가 환경변수나 저장소는 필요 없고 기존 D1/R2를 사용합니다.

관리자는 **BOM 관리**에서 제품별 기준수량과 자재를 등록합니다. 생산일정은 선택한 BOM을 기준으로
서버에서 소요량을 계산하여 스냅샷으로 저장하므로 이후 BOM 수정이 과거 일정에 영향을 주지 않습니다.
BOM 사용 중지는 기존 일정을 지우지 않습니다.

개발·샘플 의뢰, 발주입고, 기타입고, 출하는 공통 첨부 기능을 사용합니다.
판정은 자동 영상 분석이 아니라 담당자가 사진을 보고 선택하는 수동 기록입니다.
신규 의뢰/입출고 기록 저장과 사진 저장은 별도 요청입니다. 사진 업로드가 실패해도 원래 기록은 유지하며,
화면에서 실패를 알리고 사진 창을 열어 재시도할 수 있게 합니다. 같은 기록을 다시 등록할 필요는 없습니다.
첨부 저장의 revision 검사로 오래된 화면의 변경이 최신 사진을 덮어쓰는 것을 막습니다.

전체 백업은 boms/attachments 표와 첨부 객체도 포함합니다.
분석과 연결된 입고를 삭제해도 분석의 근거 사진과 판정은 보존합니다.

`0004_bom_categories_receipt_selection.sql`은 BOM의 품목 분류와 기타입고의 BOM 참조·등록 당시 스냅샷을 추가합니다.
기존 기록의 분류·입력자를 추정하거나 일괄 덮어쓰지 않습니다.
기존 수기 기타입고는 계속 조회·수정할 수 있고, 새 기타입고는 분류가 지정된 활성 BOM 선택이 필요합니다.

화면 경로는 **물류 → 입고목록**으로 통합하며 **발주입고 / 기타입고** 탭으로 전환합니다.
기존 `#/logistics/receive`와 `#/logistics/other` 주소는 각각의 탭을 열도록 유지합니다.
폼의 입력자 표시는 서버에서 기록하는 로그인 사용자와 대응하며 이름을 수정하는 입력란을 제공하지 않습니다.

## 리포트 배포

리포트는 기존 D1 데이터를 읽는 `/api/reports`를 사용하며 스키마나 추가 환경변수 변경이 없습니다.
`reports.mjs`의 집계 로직과 `public/reports.js`의 화면·차트를 기존 빌드에 포함합니다.
외부 차트 패키지나 외부 데이터 전송 없이 SVG 차트를 브라우저에서 렌더링합니다.

로그인 사용자만 리포트를 조회할 수 있습니다. 조회는 데이터를 변경하지 않습니다.
조회 범위는 최대 3년이며, 집계 결과가 20,000그룹을 초과하면 조건을 좁히도록 안내합니다.
CSV는 한국어 UTF-8을 사용하며 품목명 등에서 스프레드시트 수식이 실행되지 않도록 처리합니다.

분석은 등록기간 기준 현재 상태, 생산은 선택한 일정 종류의 시작일 기준으로 해석해야 합니다.
이 리포트는 상태 변경 이력을 복원하는 감사 로그가 아닙니다.
이미 입고확인된 발주를 다시 확인해도 최초 확인 일자·처리자·실입고수량을 유지합니다.

## 목록 검색·필터 배포

검색·필터는 기존 조회 API에 조건을 추가하며 DB 스키마나 환경변수 변경이 없습니다.
모든 조회는 로그인 인증을 유지하고, 검색어와 조건값은 SQL 바인딩으로 전달합니다.
`%`, `_`, 역슬래시는 일반 문자로 검색하며 날짜는 실제 달력 날짜와 기간 순서를 확인합니다.

의뢰 등록기간, 발주 납기기간, 입고·출고 기간을 구분합니다.
생산일정의 기존 일/주/월 기간 겹침 조회는 유지하면서 키워드·완료·일정 기준 조건을 추가했습니다.
화면은 최신 조회 응답만 적용하고 검색 결과 건수·합계를 표시합니다. 조회 조건 초기화는 데이터를 수정하지 않습니다.

`0022_quality_inspections.sql`은 규격·측정·수정이력 표와 의뢰의 규격 스냅샷 컬럼만 추가합니다. 기존 0000~0021과 기존 의뢰 데이터는 변경하지 않습니다. Sites가 새 마이그레이션을 적용한 뒤 Worker를 배포합니다. D1/R2 및 환경변수 추가·변경은 없습니다. 배포 후 품질팀장이 검사규격을 등록해야 새 의뢰에 자동으로 적용됩니다.

## 회사 계정의 R2로 사진 이전 (15.43)

기존 Site와 D1, BUCKET 바인딩은 유지하고 회사 R2에는 S3 API로 접근합니다. 새 마이그레이션은 없습니다.
회사 버킷은 비공개로 유지합니다. 서버가 업로드·다운로드를 중계하므로 공개 버킷이나 브라우저 CORS 설정은 필요 없습니다.

| R2_ACCESS_KEY_ID | 해당 버킷에 대한 Object Read & Write 키, 비밀 값으로 등록 |
| R2_SECRET_ACCESS_KEY | 해당 키의 시크릿, 비밀 값으로 등록 |
| R2_STORAGE_MODE | 복사·검증 중 native, 전환할 때 external |

키는 채팅·소스·번들에 넣지 않습니다. 이 작업 환경에 키를 전달해야 한다면 환경의 Secrets에 위 이름으로 등록합니다.
Sites 운영 환경변수는 native Sites 도구로 설정하며 INVITE_CODE와 다른 키는 그대로 둡니다. 환경변수 변경 후에는 저장된 버전을 배포해야 적용됩니다.

1. 전체 백업을 확보합니다. R2 연결 변수와 native 모드로 배포하고 관리자 설정 → 회사 사진 저장소 → 연결 확인을 실행합니다.
2. 사진 등록·수정·삭제와 확인자 서명 변경을 잠시 멈추고 기존 사진 복사·검증을 실행합니다. 3개씩 처리하며 원본·대상 데이터를 SHA-256 및 Content-Type으로 비교합니다. 원본 삭제와 기존 대상의 덮어쓰기는 하지 않습니다. 실패 시 설정/충돌 원인을 해결하고 처음부터 다시 실행할 수 있습니다.
3. 마지막 검증 완료 후 입력 중지를 유지한 상태로 R2_STORAGE_MODE=external을 설정하고 같은 버전을 재배포합니다. 새 사진 업로드·기존 사진·서명·사진이 포함된 전체 백업을 확인한 뒤 입력을 재개합니다. 전환 전 native 모드에서 새 사진이 추가됐다면 전체 복사·검증을 다시 실행합니다.
4. external 모드에서는 새 사진만 회사 저장소에 쓰며, 조회 시 회사 저장소에 없는 옛 사진만 기존 BUCKET에서 읽습니다. 회사 저장소의 403/5xx·연결 오류는 그대로 오류로 처리합니다. 원본은 별도 정리 지시가 있을 때까지 보존합니다.
5. 전환 후 native로 되돌리려면 새로 저장된 사진을 먼저 역복사·검증해야 합니다. 설정만 되돌리면 전환 후 새 사진은 보이지 않습니다.

R2의 S3 호환 규격: https://developers.cloudflare.com/r2/api/s3/api/
SigV4 구현은 AWS 공식 GET Object 예제의 서명으로 검증합니다: https://docs.aws.amazon.com/AmazonS3/latest/developerguide/sig-v4-header-based-auth.html

현재 신규 이미지는 회사 R2에 저장합니다(R2_STORAGE_MODE=external). 기존 이미지는 옮기지 않고 기존 BUCKET에서 대체 조회합니다. 사진 한 장당 최대 8MB(8×1024×1024바이트), 최대 10장입니다. 브라우저가 선택 즉시 크기를 확인한 뒤 최적화하고, 전송할 전체 크기도 검사합니다. 서버 JSON 요청 한도는 30MB입니다. 여러 사진의 전송 용량이 크면 나누어 첨부해야 합니다.

Workers에서는 Request의 redirect:error 대신 manual을 사용하고 3xx를 직접 거부해야 합니다. 로컬 Node와 운영 Workers의 차이를 포함한 R2 회귀 테스트를 확인하세요.

- 15.138 세금계산서 문서상태(기존 ERP 참고, 마이그레이션 0048: tax_invoices.issue_type·recv_status·recv_at·recv_by, vendors.tax_reverse, purchase_tax_invoices.issue_type). 발행구분 정발행/역발행: 거래처 사업자 정보에서 「역발행 거래처」(예: 삼성)를 켜면 담을 때 역발행, 역발행은 트러스빌 발행에서 빠지고 「역발행 승인 기록」(승인번호)으로 발행 완료. 상대방 수신(미확인·확인·거부)·국세청 전송/미전송은 POST /api/tax-invoices/state {ids, action: recv_confirm|recv_reject|recv_reset|nts_sent|nts_unsent|reverse|normal}로 손으로 표시(연동 뒤 자동 예정). 목록 필터 issue_type·doc(tax/free)·state(unconfirmed|confirmed|rejected|nts_pending|nts_sent), 응답 summary(매출 합계·수신자 미확인·수신 확인·국세청 전송·미전송·역발행·발행 전 건수·공급가액·세액) → 화면 아래 요약표. 문서상태 칸 = 역발행 표시 + 발행 상태 + 수신 상태. 매입 계산서 등록에 발행구분(정발행 받음/역발행).
